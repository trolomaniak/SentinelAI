# Architecture decisions

## 2026-09-30 — TASK-001 foundation

- Use .NET 10 for the initial backend solution. Agent is a console executable, Core is an empty ASP.NET Core host, and both reference a shared contracts library. Windows Service hosting, endpoints, and transport models belong to later tasks.
- Keep the dashboard as static HTML/CSS with a dependency-free Node build until its functional requirements call for a client framework.
- Run package-free executable assertions for the initial scaffold so CI can exercise the projects without external test packages. Replace or extend these with a standard test framework when application behavior warrants unit tests and NuGet access is available.

## 2026-10-01 — TASK-002 local Core authentication

- Bind Core to loopback HTTP by default. Operators can configure a different URL or HTTPS certificate through standard ASP.NET Core configuration.
- Store the first administrator in a local SQLite database. Bootstrap credentials come only from environment variables on the first start; later starts never replace that account. Hash passwords with ASP.NET Core Identity PBKDF2 at 310,000 iterations.
- Use ASP.NET Core bearer authentication with a 15-minute token lifetime and process-local Data Protection keys. Tokens become invalid when Core restarts, and no signing or protection key is written to disk. Login attempts are rate-limited.
- Keep TASK-002 integration checks in the existing executable Core test project. They exercise a real loopback server and temporary SQLite database without adding a test framework dependency.

## 2026-10-01 — TASK-003 provisional heartbeat

- Host the .NET Agent with `AddWindowsService` so one executable runs under the Windows Service Control Manager and as a console process for development. Persist a generated installation ID locally; it identifies an installation but does not authenticate it.
- Until TASK-004 provides secure enrollment, allow Agent heartbeats only to a loopback Core origin, reject non-loopback heartbeat clients in Core, rate-limit the endpoint, and mark device records `unverified`. No administrator credential is stored in the Agent.
- Use Core's server clock for `last_seen` and persist the last reported `reporting` state in the existing SQLite database. A consumer must use `last_seen` to determine freshness; TASK-003 does not define an online/offline threshold.

## 2026-10-01 — TASK-004 secure enrollment

- Treat one Core installation as one organization for the current local-first architecture. Generate and persist separate Core installation and organization GUIDs. An authenticated administrator issues a random 256-bit enrollment token that expires after ten minutes; Core stores only its hash and atomically consumes it when creating an endpoint enrollment.
- Preserve the existing Devices table and installation IDs. Store the Core-assigned endpoint ID, organization/Core association, and a hash of a distinct 256-bit Agent credential in an additive EndpointEnrollments table. A repeated enrollment for the same installation returns `409` without creating a duplicate or rotating the credential.
- Authenticate enrolled heartbeats with a separate `SentinelAgent` authorization scheme and reject anonymous updates to enrolled installations. Keep anonymous heartbeat limited to unverified loopback devices for TASK-003 compatibility. LAN enrollment and heartbeat require HTTPS; the Agent additionally requires TLS 1.3, normal certificate validation, and an explicit Core certificate SHA-256 fingerprint. Full mTLS certificate lifecycle management remains outside TASK-004.
- Bind Agent enrollment state to its installation ID, Core origin, and certificate fingerprint. Protect the credential with Windows DPAPI under the service account; use private file permissions for Unix development tests. Do not log enrollment tokens or Agent credentials.

## 2026-10-01 — TASK-005 endpoint inventory

- Send inventory through a separate authenticated Agent API after an enrolled heartbeat succeeds. The Agent refreshes every six hours and retries inventory failures after five minutes without interrupting heartbeat delivery. Anonymous loopback Agents cannot submit inventory.
- Keep only the newest report per Core-assigned endpoint ID in SQLite, ordered by Agent collection time. Validate field sizes and disk counts before storing reports; keep inventory separate from heartbeat freshness and health.
- Limit Windows collection to bounded system metadata queries for host, OS, CPU, physical memory, fixed local disks, and available firewall profile settings. Represent unavailable values as unknown instead of failing the Agent. Do not inspect arbitrary file contents or launch external scanners.

## 2026-10-02 — TASK-006 device dashboard

- Serve the dependency-free dashboard from Core's origin, with the static assets copied into Core build and publish output. Keep administrator bearer tokens only in browser memory and require HTTPS for non-loopback dashboard sign-in. No cross-origin API permission is introduced.
- Expose administrator-only list and detail views of enrolled endpoints. Join enrollment identity, Core heartbeat time, and the latest inventory without returning credentials or raw database records. Unverified loopback-only devices are excluded.
- Derive connectivity health from Core's last-seen time: healthy up to two minutes, warning up to five minutes, offline thereafter, and unknown before any heartbeat. Keep last reported firewall settings separate from connectivity health and label missing inventory as unknown.

## 2026-10-02 — TASK-007 deterministic rules

- Keep detection in a dependency-free stateless rules library with individually testable rules and explicit normalized observation inputs. Preserve the inventory timestamp and typed evidence; evaluation has no clock or LLM dependency and never performs remediation.
- Extend inventory with optional bounded Windows configuration observations. Do not infer default settings, effective runtime protection, account privilege, Internet exposure, or patch compliance. Missing, unreadable, malformed, and unsupported observations remain unknown; prerequisite checks suppress inapplicable UAC/RDP findings.
- Derive current structured findings from the newest accepted persisted inventory through an administrator-only API. This avoids a second snapshot store or premature incident lifecycle schema. Older uploads cannot replace findings, newer normal state clears them, and repeat reads are deterministic. Incident history/status and risk scoring remain later tasks.

## 2026-10-02 — TASK-008 persistent alert tracking

- Persist one tracked posture alert per enrolled endpoint and rule, in the same SQLite transaction as the accepted newer inventory. Preserve first observation and update the latest positive evidence/time; bootstrap existing inventory into alert tracking idempotently. Keep TASK-007 current findings as a separate, unchanged API.
- Treat alert status as an administrator decision with durable actor/time history. Repeated positive detections preserve Open, Investigating, and Accepted; a strictly newer positive observation reopens Resolved. Normal or unknown telemetry never automatically resolves an alert. No endpoint remediation occurs when status changes.
- Use version-checked status writes to reject stale administrator edits. Require existing administrator authentication and secure transport, and bound list pagination. Extend the same-origin, memory-token dashboard with alert list/detail/status controls without adding dependencies or premature scoring/correlation.

## 2026-10-02 — TASK-009 explainable risk policy

- Compute endpoint risk deterministically from explicit inputs and a centralized, validated policy. Show severity, confidence weight, asset criticality, declared exposure, observation age, remediation state, and confirmed rule-group correlation contributions. Confidence is a policy weight for reported configuration rather than a calibrated probability; missing asset/exposure context is an explicit default assumption.
- Keep the status multiplier at one for Investigating and Accepted because those states provide no remediation evidence; Resolved sets it to zero until a newer positive observation reopens it. Age multipliers stay positive, while explicitly configured confidence discounts and integer rounding can yield a zero displayed score. Correlation uses distinct supported rule groups confirmed in the same latest snapshot within the policy window, excluding older or contradictory historical evidence.
- Calculate scores on request from a consistent SQLite read snapshot instead of persisting a second score state. Apply an explained endpoint score cap and use the highest endpoint score for organization prioritization, with observation coverage alongside it. Unknown telemetry and a zero score never establish safety. Operator configuration provides per-endpoint criticality/exposure without introducing new remediation or AI workflows.

## 2026-10-02 — TASK-010 signed subscription leases

- Use built-in ECDSA P-256/SHA-256 (ES256) as the asymmetric equivalent permitted by TASK-010 and the product specification. A versioned compact JWS signs both the protected algorithm/key ID header and the bounded lease payload. Verification accepts one fixed algorithm, P-256 public keys, and fixed-length P1363 signatures; no algorithm negotiation or new crypto dependency is introduced.
- Keep the private-key signer in the separate cloud License API. Core references a public-only verification library and locally provisioned SPKI public PEM trust anchors, including overlapping key IDs for rotation. Bind leases to the organization and Core installation GUIDs already persisted by enrollment; no new identity or database migration is introduced.
- For the initial development issuer, map a high-entropy activation credential hash to server-side configured entitlements. Clients request only their bound identity, never the plan, feature list, limit, or duration. Issue exactly seven days from server time and enforce the same maximum duration and exact expiration boundary locally. Generate development keys automatically outside tracked source; tests use generated temporary keys and synthetic identities.
- Expose authenticated, bounded, uncached local verification and distinguish invalid, future-issued, identity-mismatched, valid, and expired leases. Only verified, identity-matching valid/expired claims are returned. Keep renewal, persistence, clock rollback protection, grace/Safe Mode, billing, and license enforcement outside TASK-010; a missing or invalid lease does not stop monitoring.

## 2026-10-02 — TASK-011 offline licensing and Safe Mode

- Keep an explicit FULL/GRACE/SAFE_MODE/RECOVERING state machine in Core. GRACE ends at the earlier of signed expiry and signed issuance plus seven days, with SAFE_MODE at the exact boundary. Recovery retains the underlying state's permissions until validation succeeds; a replay never resets the deadline to local receipt time. The current License API has no revocation signal, so generic `401` does not imply REVOKED.
- Add opt-in renewal against one operator-configured issuer origin using a separate protected activation credential file. Send only persisted Core/organization IDs, disable redirects, preserve normal TLS verification, and bound requests, response size, and complete timeout. The private signer stays exclusively in License API; public trust is still explicitly provisioned. Preserve `/license/verify` as stateless local verification.
- Persist the signed lease, signed validation baseline, outcome, and effective UTC high-water in an additive singleton table in Core's existing private SQLite database. Reauthenticate the lease before deriving permissions. Combine UTC, signed server issuance, persisted floor and monotonic elapsed time to resist obvious rollback without lowering the floor for old signed tokens. This is bounded protection, not defense against privileged storage replacement or a perfect clock while powered off; retain an erroneous forward jump conservatively rather than opening a replay reset.
- Preserve telemetry, deterministic local rules, alerts, incident/history access and emergency export in every state. Withhold optional signed feature grants in SAFE_MODE without inventing premium gates for current local APIs. Add a bounded authenticated JSON incident export from one consistent read snapshot; no vendor outage can disable Core monitoring. No new dependency, destructive migration, lease wire-format change, billing, or automatic trust discovery is introduced.

## 2026-10-02 — TASK-012 selected-alert cloud AI

- Add a separate AI Gateway for one assistive selected-alert explanation. The provider API key is read only from gateway process configuration; Core carries a distinct gateway credential and references only shared contracts. Fixed outbound origins, verified TLS, no redirects, bounded timeouts/bodies, gateway client authentication and rate/concurrency limits constrain paid requests. Use a direct structured-output HTTP adapter rather than adding a provider SDK.
- Project existing alert evidence through an explicit allowlist for the 13 built-in rules. Send only rule/severity, booleans or small integers, platform and coarse observation freshness. Do not send names, IDs, timestamps, raw logs, history or arbitrary strings. Independently validate the same narrow schema in the gateway, and keep incident JSON separate from model system instructions.
- Return strictly bounded structured explanation, impact, investigation/remediation suggestions and qualitative confidence/uncertainty under a fixed assistive label. Render text literally and keep it separate from deterministic detection/status. AI is read-only, has no tools or endpoint executor, and does not persist analysis or context. Provider failures never prevent local alert access/review.
- Treat this new cloud-dependent feature as signed `cloud_ai` permission under TASK-011's existing effective capabilities. Safe Mode and missing entitlement withhold cloud requests while preserving the local security baseline. Require an explicit supported model at gateway deployment; tests use generated development credentials and synthetic provider HTTP, without production keys or real customer data.

## 2026-10-02 — TASK-013 local security reporting

- Generate standalone HTML from one consistent SQLite read snapshot and the existing deterministic risk policy. Reporting is part of the local security baseline, available in Safe Mode without cloud AI or issuer calls. Keep the dependency-free architecture; browser printing can save HTML as PDF without adding a PDF service.
- Separate selected-period retained incident activity from current risk, health, coverage and unresolved posture. Use inclusive UTC calendar dates and durable status history for resolutions, preserving first-observed counts after later observations and disclosing reopening. Latest inventory, heartbeat and alert evidence cannot reconstruct historical posture, severity, fleet membership or every observation; score trend remains explicitly unavailable until history exists.
- Project only necessary local fields and allowlisted typed security evidence, omit authentication/licensing/configuration material and history actors, and encode every HTML value. Use static CSP-protected attachment output, deterministic ordering/formatting and explicit work/output limits without silently incomplete aggregate counts. No new persistence, scheduler, migration or remediation capability is introduced.

## 2026-10-02 — TASK-014 signed update foundation

- Use a distinct public-only update library with strict bounded JSON and fixed P-256/SHA-256 signatures over format, key ID and all claims. Explicit environment/channel/artifact/version/public-root policy authorizes one update; development and production trust remain separate and numeric version floors reject replay/downgrade. A separate development-only signer generates keys outside source; production signing, embedded roots, automatic discovery and cloud downloading are absent.
- Verify SHA-256 and signed byte length while creating the private copy used for bounded ZIP validation/extraction. Reject path collisions/traversal, Windows aliases/ADS, symlinks/reparse points and expansion bombs before service stop. Keep persistent AppData/DPAPI state outside the code directory, and retain the stable installation path/service account.
- Install through an explicit service lifecycle adapter, an exclusive per-installation lock, sibling staging/backup and a durable journal. Health gates the signed installed receipt; failed install/start/health/cancellation restores old code with an independent recovery deadline. Recovery validates journal/manifests and handles rename interruption windows; failed rollback retains recoverable state. Concrete Windows service/installer wiring belongs to later integration; no adapter assumes health, dependency, destructive migration, scheduler or release host is added here.

## 2026-10-02 — TASK-015 local Windows pilot workflow

- Keep the first pilot co-located: Core runs as the installing operator's loopback console process, and only Agent is registered as a Windows Service under stable, limited LocalService. Reuse existing hosts and credentials instead of adding a Core service dependency, certificate issuer, firewall exception, migration or automatic upgrade. Document the shared account/DPAPI scope and require separate real Windows acceptance.
- Separate protected Program Files code from ProgramData configuration/state. Explicit bounded allowlisted `--config` files are authoritative over ambient host settings. Initial administrator input is confined to the Core child environment; one-use enrollment uses a fixed ACL-restricted handoff removed after persisted validation. A nonsecret endpoint receipt derived from enrollment selects the exact device for verification; passwords/tokens never enter service arguments, normal configuration or logs.
- Reuse public update verification and bounded extraction through `prepare` before service changes. Operators provision public trust out of band and trust bootstrap tools through their delivery channel. Reject unknown services, changed code/configuration, links/untrusted writable paths and overwrites; uninstall removes only the matching service and preserves all state/code. Reinstall with identical signed code and the same account retains identity; production signing/Authenticode and transactional update service wiring remain separate concerns.

## 2026-10-03 — TASK-016 native desktop foundation

- Use .NET 10 WPF for the Windows x64 desktop executable, with native window chrome and an MVVM shell. Keep views, resources and Windows lifecycle composition in `SentinelAI.Desktop`; keep navigation, observable state and the local Core service boundary in a separate dependency-free portable Foundation project so their behavior can be tested without Windows. Browser embedding and dashboard screen migration are absent from this task.
- Limit the initial Core client to a fixed loopback health endpoint with no UI-configurable destination, credentials, redirects or proxy routing. Connection checks are bounded and asynchronous; Core unavailability does not prevent the desktop shell from opening or navigating. Window closure cancels pending work and disposes the client, and no desktop password/configuration store is introduced.
- Use semantic dynamic theme resources, WPF logical units and a PerMonitorV2 manifest for scaling and future theme changes. Cross-build the Windows projects in the existing solution, run portable tests locally, and require separate actual Windows WPF/EXE acceptance; a Linux build or simulated viewport does not establish native Windows launch or physical multi-monitor scaling.

## 2026-10-03 — TASK-017 managed Core Windows Service

- Reuse Core's ASP.NET Core host with official context-aware WindowsServices integration, preserving console development mode and all API/security contracts. Service mode requires the existing strict nonsecret configuration, an initialized administrator and a fixed executable content root. Initialize administrators through the existing console launcher; reject bootstrap credentials in service mode and bound graceful host shutdown to 15 seconds.
- Register fixed `SentinelAICore` under the limited virtual account `NT SERVICE\SentinelAICore`, keeping Agent's LocalService/DPAPI identity unchanged. Re-verify the exact signed pilot code before installation, retain the pilot receipt and add a separate administrator-owned service receipt. Select delayed automatic startup and SCM restart delays of 5/15/60 seconds with a one-day reset; clean stops remain successful. Virtual accounts can authenticate to domain resources as the machine account; this local workflow grants no additional network access or ambient outbound authentication.
- Keep existing code/configuration/SQLite paths. Core gets code read/execute, protected configuration/receipt read, and narrowly scoped SQLite write/create access. The data parent grants no DeleteChild and only newly created files inherit Modify; protected files cannot be replaced through their parent. Permit the virtual SID only within the explicit Core data root when validating runtime ownership, preserving existing Agent trust defaults.
- Bind installation/start health to the exact SCM process and configured loopback listener, with a bounded complete HTTP response and no redirects/proxy/cookies. Ownership checks remain mandatory for stop/removal, while corrupt/missing SQLite or unknown runtime files cannot prevent safe service stop/removal. Removal preserves bytes and restores console ACLs. Native SCM/NTFS/desktop lifetime acceptance is separate from portable policy/lifecycle tests; automatic upgrades, schema/account migration and future desktop screens remain outside this task.

## 2026-10-03 — TASK-018 native administrator setup and sessions

- Keep administrator creation authoritative in Core and preserve the existing privileged installation boundary. Native Desktop invokes a one-shot, trusted local Core command with bounded credentials on private redirected stdin; the same password hasher/immediate SQLite transaction creates one account and never resets an existing one. Read-only Core state, not HTTP unavailability, detects first run. Initial setup may use a separate UAC-approved window; no anonymous network bootstrap or uninitialized service hosting is introduced.
- Reuse Core login and administrator-session routes. Keep the short-lived bearer private in Desktop memory, discard refresh tokens, clear native password input/buffers and invalidate obsolete requests on sign-out/close. Revalidate sessions periodically; expiry, restart, `401` or connection loss returns to signed out with explicit reconnect. Core rejects remote plaintext login before reading the body.
- Use fixed local installation/origin and administrator-controlled SCM registration as the ordinary service trust anchor. Verify the actual established TCP peer tuple/PID before HTTP writes credentials, instead of relying only on an earlier listener check. Ordinary users need no SQLite/setup-file access to sign in; console/helper access retains operator filesystem authority. Do not change service ACLs/identity, add dependencies/migrations, or implement later native data screens.

## 2026-10-03 — TASK-019 native Devices

- Reuse the private authentication client's session, trust gate and HTTP handler for read-only device APIs. Views/view models receive typed public data and outcomes only; no token exposure, persistence-store access or credential copying is introduced.
- Add an optional inventory timestamp to the existing Core list DTO, derived from the retained report without a migration. Filter/sort the full accepted list before 100-row UI paging; explicitly reject oversized responses/fleets instead of silently truncating them. Core retains all heartbeat thresholds; configured posture remains a separate nullable observation.

## 2026-10-04 — TASK-020 native Alerts and incidents

- Keep persistent alert lifecycle, positive-observation reopening, history and optimistic versions entirely in Core. Add only an optional endpoint filter to its existing list query so endpoint/severity/status filtering precedes the page and count; retain existing defaults, order and public DTOs without a migration.
- Reuse the same private Desktop authentication owner and verified transport for bounded typed reads and explicit versioned status writes. Render all dynamic data as literal native text. On conflict, fetch current detail once and require a fresh operator choice; on an uncertain write response, require a detail refresh and never retry the write automatically. Status changes record review decisions and never modify endpoint configuration.

- Reference the existing first-party immutable scoring records from portable Desktop Foundation and consume Core's existing public projections. Keep calculation, effective policy, coverage and ranking authoritative in Core; native 50-row pages and independently timestamped detail preserve decimal factors without invoking `RiskScorer`, inferring missing context or introducing historical trends.
- Treat generated report HTML as an opaque, bounded, owned memory document with strict UTF-8 and required Core response headers. Expose only metadata to the native view; an explicit native destination picker precedes a same-directory staged write/atomic move of the exact Core bytes. Do not embed, recompose or automatically open HTML. Date edits, leaving Reports, sign-out and close cancel pending work and erase retained buffers; already saved files remain operator exports. Preserve Core's existing privacy projection and Safe Mode behavior without a new package, scorer/report backend change or database history.

## 2026-10-08 — TASK-022 native AI, licensing and Settings

Keep signed state, permitted capabilities, issuer/gateway destinations, all credentials and minimized cloud context authoritative in Core. Renewal and AI are explicit, bounded and never automatically replayed; an uncertain renewal requires a status refresh before another attempt.
- Implement local AI consent as an off-by-default memory-only session setting, reset on sign-out/close. Consent cannot grant entitlement or choose a destination. Clear assistive results on selected-alert/version/navigation/permission changes and render only literal typed suggestions without execution or persistence. Native Settings exposes public licensing/runtime facts and the existing health check without editing protected Core configuration; local security pages stay independent of optional failures.

## 2026-10-08 — TASK-023 browserless Desktop lifetime

- Support native Desktop as the normal production interface; retain the existing dashboard only for development/diagnostic compatibility without changing HTTP contracts. Keep GUI, Core and Agent lifetimes independent: window/tray exit clears the local session and stops only the GUI, while reopening performs fresh authentication.
- Elect one normal GUI per existing Windows user and interactive session using current-user/session ownership and fixed bounded activation-only IPC. Keep administrator setup separate; accept no credentials, paths, destinations or serialized session data through activation. An unreachable owner fails safely without creating another authenticated GUI.
- Persist only nonsecret, off-by-default current-user tray/notification choices and an exact owned quoted Desktop Run command. Preserve foreign/malformed registrations, observe read-back and honor the Windows command-length limit. Read fixed Core/Agent SCM status with query-only access and bounded observation; generic stopped-service notifications are optional and frequency-limited. No service control, automatic authentication, protection dependency or new package is introduced.

## 2026-10-09 — TASK-024 trusted single executable setup

- Deliver one native Windows x64 `SentinelAI-Setup.exe` with administrator elevation, containing an ordinary self-contained WPF host and its immutable, hash-bound deployment resources. Before loading .NET, the native bootstrap validates resource paths/sizes/hashes, creates fresh Admin/System-protected ProgramData staging and launches only the exact protected host. Use Windows SDK `cl`/`rc` with a static CRT and System32 DLL resolution; no third-party installer framework or runtime dependency is added.
- Do not use elevated .NET single-file cache extraction as the bootstrap trust root. [.NET 10's extractor](https://github.com/dotnet/runtime/blob/v10.0.0/src/native/corehost/bundle/extractor.cpp#L295) reuses existing cached files by existence before managed startup. Native setup clears inherited runtime code-loading overrides and supplies private temporary storage before CLR launch. Setup-only Core/Agent/Updater publishing uses ordinary self-contained directories so SCM runtimes stay in authenticated, protected code. The manual pilot publisher's default is preserved.
- Reuse the existing signed-package verifier, pilot path/ACL/enrollment code, Core service ownership/health policy and Core-owned administrator stdin helper. Pin a build-provisioned public root independently from the embedded package bundle; never adopt a ZIP-selected key or embed signing keys/customer credentials. Fix the installation to the Desktop-supported loopback origin and Program Files/ProgramData paths; refuse existing/unknown targets rather than implement repair, upgrades or migrations.
- Create the administrator before starting Core. Issue the Agent's one-use token through the same native established-connection owner check as Desktop before sending administrator credentials. PowerShell receives only the token through bounded private stdin. Preserve the original pilot credential workflow while adding an optional explicit one-use token to its installer; no Core/Agent HTTP contract changes. Credentials and session material are never arguments, environment, logs or permanent setup configuration.
- Load authenticated embedded installer code as in-memory PowerShell modules without changing execution policy, application control or language constraints. Preserve inherited security policy. Only Desktop/shortcut code receives Users read/execute; service state retains existing limited-account ACLs. Open Desktop through a verified unelevated Explorer shell or provide an explicit Start Menu instruction. No automatic login, startup preference, service control in Desktop, remote provisioning or next task is introduced.

## 2026-10-09 — TASK-025 whole-deployment maintenance

- Replace the entire fixed Program Files code root in one signed `sentinelai-deployment-win-x64` transaction. Four sequential component transactions would expose mixed versions and partial rollback. Reuse the existing updater's verified private ZIP, exclusive lock, durable journal, sibling backup and bounded lifecycle adapter; keep the protected native Setup host outside the replaced tree. Deployment-only archive/workspace bounds accommodate four runtimes without broadening existing component limits.
- Pin candidate verification to the protected installed public key, key ID, environment and channel. Strict upgrade still requires a newer version. Explicit repair requires exactly the authoritative installed version and, once present, exactly the authenticated installed package claims. A retained-data reinstall uses an explicit empty-target restore operation with the original protected version floor; it cannot authorize a downgrade by changing that floor.
- Keep all persistent state outside the transaction. Atomically snapshot only public ownership receipts under administrator-protected Setup data so version/executable hashes can follow either candidate or restored code across interruption. Validate fixed SCM registrations/accounts and unchanged configuration before mutations; apply execute-only service ACLs, verify actual PID-bound Core HTTP health and retained Agent enrollment before committing. Failed rollback retains its journal/snapshot for explicit recovery.
- Uninstall preserves SQLite/security history, configuration, enrollment and license state by default. Remove data only through a separate native opt-in and exact `DELETE` confirmation. Protected retained ownership allows explicit restoration with the same administrator/endpoint identity; foreign services, writable paths, links and installations without ownership proof are refused. No data migration, public HTTP contract, automatic update scheduler or new runtime dependency is introduced.

## 2026-10-12 — TASK-026 continuous posture monitoring

- Detect configuration changes with one-shot, thread-agnostic Windows registry change notifications on exactly the 16 keys the existing collector reads; a test enforces that equivalence. Watch an absent key through its nearest existing ancestor subtree, never a hive root or top-level key, and add five-minute verification for missed notifications. Notifications carry no data and only trigger a settled re-read of the same bounded allowlist. Do not use polling loops, WMI/ETW/event-log subscriptions or a new dependency; the Windows event pipeline remains TASK-027.
- Deliver a detected change as a fresh full `InventoryReport` through the existing authenticated inventory route, not a new posture-only API. Core's newest-report ordering, unchanged rules, alert lifecycle and next-read Risk remain authoritative. No Core, contract, schema or migration change is required.
- Compare against the posture Core last acknowledged and keep one in-memory pending delivery, not a queue. Coalesce bursts with a two-second quiet period (at most ten seconds), space change-triggered uploads by 30 seconds and retry failed uploads after the existing five minutes. Never shorten outage heartbeat backoff. Restart relies on startup reconciliation instead of persisted retry state, and the six-hour reconciliation stays independent of change uploads.
- Monitoring intervals are ordinary bounded host configuration, outside the pilot `--config` allowlist, so installed services use the defaults. Native acceptance changes `RunAsPPL` because Windows applies it only at boot, then restores the original value. It does not weaken a live protection such as the firewall on the runner.

## 2026-10-13 — TASK-027 continuous Windows security event pipeline

- Collect a compiled catalog of 16 selections (12 kinds on the Security, System, PowerShell/Operational and Defender/Operational channels) through named-field selectors only; configuration cannot widen it and Core ignores other tuples. Identities are SIDs only (`S-1-0-0` becomes null; no account, domain or workstation names). Free text that can carry secrets or personal paths (`ImagePath`, `AccountName`, Defender 5007 values) is derived into closed vocabularies or a leaf file name, never copied, and message text, event XML and positional properties are never rendered. A present but invalid value becomes null and is counted; it never suppresses the event.
- Read each channel with a polled `EventLogReader` whose catalog-generated XPath filters provider, event ID and level on the server and also selects `EventRecordID` of the acknowledged position and of the newest record, so `Seek(bookmark, 0)` always targets a member of the result set. Every pass that reads from a position still inside the log verifies that record's creation time (an untimed position by seeking on it), and a failed seek falls back to a counted `EventRecordID>=` filter. The decompiled EventLog 10.0.12 sources showed that the bookmark constructor seeks +1 without a strict flag, that `ReadEvent()` without a timeout waits indefinitely and that the local session cannot cancel another reader, so the design uses `Seek(bm, 0)`, `ReadEvent(10 s)` and `CancelReading()` at stop. `EventLogWatcher` was rejected because a throwing thread-pool callback crashes a service that has no SCM recovery, an overwritten bookmark becomes a silent gap and backpressure would block a pool thread; ETW and raw wevtapi P/Invoke would add a subscription or unsafe-interop surface for guarantees the public reader already provides.
- The Windows log is the buffer: one prepared batch, no reads while it is pending and no event payload on disk. Positions (record number plus creation ticks) move past collected records and gaps only after Core acknowledges them and are then saved at once; a pass with nothing to collect advances without a request. Overwrites, resets (with the new generation read in the same pass and an `overwritten(1, oldest−1)` gap when its first records were already lost), coverage starts and dropped records are gap items inside the same batch, detected again with the same key after a crash, and a per-channel reserve keeps every batch within 32 gaps. Batch-level 400/404/405/413/415 holds the batch instead of dropping it.
- Core checks transport and the Agent credential before reading the body, reads at most 256 KiB with strict JSON options and validates items individually (unknown ignored, invalid rejected, and an invalid observation recorded as a `rejected` gap). One immediate transaction stores observations under `UNIQUE(EndpointId, Channel, RecordId, TimeCreatedUtcTicks)`, merges gaps, derives `CoverageRestart` from earlier coverage and upserts status with a staleness guard; accepted/duplicates count observations only, ignored/rejected count every item kind. Retention by receipt time is 10,000 observations and 1,000 gaps per endpoint and 30 days with bounded sweeps. The only read surface is the additive status-only route `GET /api/admin/devices/{endpointId}/event-sources`; no rule, report or AI context uses observations before TASK-028.
- `Agent:EventPollInterval` (5 s, 100 ms–5 minutes) is the only new option, the other event intervals derive from it, and it stays outside the pilot `--config` allowlist; there is no license gate. The installed LocalService Agent reports Security as `accessDenied`: any read grant (a per-service SID ACE, Event Log Readers membership or a broader change) is a security-boundary decision pending owner approval, and the pipeline starts collecting Security at its next one-minute retry after a grant, without code change. The Agent references `System.Diagnostics.EventLog` 10.0.12 explicitly, the version already resolved transitively, so the package graph is unchanged.

## 2026-10-14 — TASK-028 runtime event detections

## 2026-10-18 — Bounded Updater preparation and CI stall probes

- Bound the out-of-process Updater `prepare` twice: the Updater stops itself after 5 minutes (exit code 2, partial output and private copy removed), and its PowerShell caller kills it after 330 s and never waits unbounded for end of output; the Setup host likewise waits at most 5 s for end of output once its worker has exited. - Size the limit for slow healthy hardware, not for the fastest disk. A first 90 s limit would have failed a 5,400 rpm disk on every attempt, and the CI probes measured 60–75 s per Core preparation inside Setup on the runner's system disk. On CI the 300 s install wait still ends a stalled install first; the probes and the descendant cleanup cover that case.
- Extract package files without write-through and keep the existing flush to disk after each file. Write-through forced every block (about 6,300 writes for Core, each also updating NTFS metadata) to stable storage, but a partially written file is discarded on failure or recovery anyway, so only the per-file flush gives durability. Probe output is numbers and allowlisted words only.
- Do not raise the 300 s `setup-windows` install limit or the 900 s lifecycle limit yet. The first probes, on passing runs, show Setup's work I/O-bound on the runner's system disk (the install finished at about 250 s of 300 s), which corrects the earlier reading of these failures as stalls. ## 2026-10-19 — MVP-1 central Core on the local network

Implements the owner decisions above (TLS policy, pin-only trust, Domain/Private + LocalSubnet firewall rule, Agent-only routes on the local-network listener) for Windows 10 22H2 and Windows 11 x64.

- **Certificate key storage: the `LocalMachine\My` certificate store with a CNG machine key and its access list**, not a protected file under Core's ProgramData directory. SChannel serves TLS only with a persisted key: a PFX file would have to be imported into a key store at every Core start (the service profile's store), which writes the key again outside our control, while an ephemeral import fails as a Windows TLS server. The store keeps the key non-exportable and lets Windows apply its access list; Core reads only the public certificate by its SHA-256 and SChannel uses the key under Core's identity. The access list is part of the key's creation (`NCRYPT_SECURITY_DESCR_PROPERTY` in the creation parameters, protected DACL: SYSTEM and Administrators full control, `NT SERVICE\SentinelAICore` read), so no default-ACL window exists. The certificate is added to `LocalMachine\My` only; no trusted root or CA store is touched. Trade-off: the certificate lives outside the SentinelAI data root, so Setup tracks it by the pin in Core's protected configuration and deletes it explicitly on confirmed data removal.
- ECDSA P-256 rather than RSA 3072: smaller and faster to sign, supported by SChannel on Windows 10 and 11 for TLS 1.2 (ECDHE_ECDSA with AES-GCM) and TLS 1.3. Self-signed, 10 years, subject and DNS names the computer's DNS host name and FQDN, server authentication only, not a CA. Names are informational because Agents trust only the pin.
- The elevated Setup host (C#, .NET 10) creates the certificate before Core is prepared and passes only its public SHA-256 to the PowerShell worker, which checks that the certificate and key exist before writing the pin into Core's protected configuration. If Core preparation fails, the host removes the unreferenced certificate; a later failure keeps it with the partial installation, like other retained state. Confirmed data removal deletes it in the PowerShell uninstall step, before the data root, while the pin can still be read.
- Configuration: two keys in Core's protected `--config` file, `SentinelAI:LocalNetworkPort` (`"5443"`) and `SentinelAI:LocalNetworkCertificateSha256`, present together or not at all; both are part of the configuration hash in the Core service receipt. An installation keeps its role through upgrade and repair: local-only (including installations from before MVP-1) stays local-only. Enabling the role later is not offered. Every strict reader of that file accepts only these two shapes: Core (a valid port with an uppercase pin), and the PowerShell installer and the Desktop/Setup installation trust check `InstalledCoreConfiguration` (exactly port `5443` with an uppercase pin).
- TLS gate: Kestrel enables TLS 1.2 and 1.3 only; a connection middleware after the handshake accepts TLS 1.3 with `TLS_AES_128_GCM_SHA256` or `TLS_AES_256_GCM_SHA384` and TLS 1.2 with ECDHE (ECDSA or RSA) and AES-128/256-GCM, and aborts anything else before HTTP with a log line naming only the protocol and suite. TLS 1.3 ChaCha20-Poly1305 is also refused so that one AES-GCM policy applies to both versions; Windows negotiates AES-GCM. The listener is HTTP/1.1 only.
- Route gate: the TLS middleware marks accepted connections; the first HTTP middleware answers `404` with no body for anything but `POST` to the five Agent routes, before static files, health, authentication and administrator endpoints. Enrollment and heartbeat bodies are now bounded to 16 KiB (they were bounded only by Kestrel's default).
- A missing or unusable certificate, or a port another program holds when Core starts, does not stop Core: it keeps serving the local Desktop and Agent on loopback, logs that the listener is disabled and reports it in `GET /api/admin/local-network`, so local monitoring continues. Kestrel binds every endpoint or none, so Core first binds and releases the port before adding the listener; only a program taking the port in the moment between that check and Kestrel's bind can still fail the start, and the service's restart then finds the port taken and starts loopback-only.
- The listener is HTTPS on every IPv4 interface (`0.0.0.0:5443`), not `ListenAnyIP`. Agents use IPv4 addresses (Settings shows only IPv4), and Windows keeps separate IPv4 and IPv6 wildcard ports: with only a dual-mode `[::]` socket, a program started later could bind `0.0.0.0:5443` and receive every Agent's connection (the pin would still refuse it) while Settings showed the listener as listening. Holding the IPv4 wildcard port makes that bind fail instead.
- Setup follows the same rule. Only a new central service refuses a taken port, checked by binding without listening so the elevated worker never raises a Windows Firewall prompt for PowerShell. Start, Restart and Setup health do not require the local-network listener while another process holds the port or Windows has reserved it in an excluded port range (read from `netsh`, so no check races Core's own bind); repair, upgrade and recovery are therefore never blocked by it. Setup's health checks require the local-network listener only while the configured certificate exists, so an operator's deletion of the certificate cannot block repair.
- Firewall: one rule with the fixed unique name `SentinelAI-Core-LocalNetwork` (NetSecurity cmdlets): inbound TCP 5443, program `SentinelAI.Core.exe`, remote `LocalSubnet`, profiles Domain and Private, edge traversal blocked. Fresh installation refuses a computer where it exists, and inspection treats it as installation state needing inspection; repair and upgrade recreate it exactly if missing or changed; uninstall removes it.
- Desktop reads addresses, port and fingerprint from the additive administrator route `GET /api/admin/local-network` (loopback only, like every administrator route). Addresses are the active IPv4 unicast addresses without loopback and link-local, at most 16.
- Agent: pin-only trust as decided; with a pin the Agent enables TLS 1.2 and 1.3. Without a pin, full validation and TLS 1.3 only remain. The legacy pilot PowerShell installer's remote token request keeps its stricter chain-plus-pin check; it cannot reach administrator routes over the local-network listener anyway, and MVP-2 replaces it with enrollment codes.

## 2026-10-20 — MVP-2 Agent installer, enrollment codes and uninstall

- **Code format v1:** `SAI1-` and Crockford Base32 (case-insensitive, O/I/L tolerated) over version, big-endian port, 32-byte pin, 32-byte token, address length and ASCII address, closed by the first 4 bytes of SHA-256 over `SAIE` and the payload. The checksum catches typing errors; it is not a signature, and the pin inside the code is what authenticates Core. Addresses are a DNS name (IDN as A-labels) or a canonical IPv4 address.
- **Address choice:** Core offers its DNS name and FQDN with whether each resolves to one of its own IPv4 addresses, and its IPv4 addresses; the recommendation is the first resolving name, else the first IPv4 address. The administrator can pick any offered address; Core refuses others.
- **Pre-check before change:** a new anonymous Agent route `POST /api/agent/enrollment-check` answers whether a token can still enroll without consuming it, so Agent Setup can refuse expired, used and revoked codes before installing anything. It reveals only whether a guessed 256-bit token is valid, which is infeasible to exploit, and is rate-limited like enrollment.
- **Remove computer:** a removal timestamp on the endpoint's enrollment; authentication refuses it, read models exclude it, history rows stay. Deleting rows would lose report history the pilot keeps. Core records whether each enrollment arrived over the local-network listener (`EnrolledOverLocalNetwork`) and refuses (`409`) to remove an endpoint that enrolled over loopback, which is the central computer's own Agent: a removed installation ID can never enroll again, and Agent Setup refuses the central computer. Enrollments from before MVP-2 have no record and are treated as the central computer's own; the pilot has no earlier local-network endpoints in the field.
- **Address length:** code addresses are at most 180 characters, so the longest code (489 characters) plus a line break stays within the 512-character parser limit.
- **Separate Agent product roots** (`%ProgramFiles%\SentinelAI Agent`, `%ProgramData%\SentinelAI Agent`) instead of the full installation's: the products have different owners and lifecycles, and the full Setup's ownership checks forbid foreign entries in its roots. Windows has one `SentinelAIAgent` service, so a computer has one Agent: Agent Setup refuses any existing Agent service, including the central computer's; the full Setup refuses Agent Setup's Agent.
- **Windows Apps uninstall runs an installed copy of the Setup EXE**, kept in an administrator-only folder. A native entry point is required: starting the .NET host directly would let user-controlled `DOTNET_*` variables reach an elevated process. The wrapper hands its own image to the host as a read-only, inherited handle that denies writers, renames and deletion, after checking by file ID that it is the file the process was mapped from, so no file swapped into the download path after launch can become the installed copy. The cost is the Setup file's size on disk (documented). A running copy is deleted at the next restart.
- **Rollback over retry:** any Agent Setup failure after its first change removes everything it created on the computer, which it proved fresh first. An enrollment Core never acknowledged may still have consumed the code; the exit code tells the administrator to issue a new one.
- **Agent Setup's folders (`AgentRoot` ACL):** Administrators and SYSTEM full control and the Agent service read, with no entry for the installing account (the pilot's `Container` kind adds one, which made every later check by another administrator or by SYSTEM fail). The ownership receipt is written first, so any partial state is owned and removable; a failed removal after a failed install is its own exit code (12).
- **Removing a running installed Setup:** the wrapper denies writing, renaming and deletion while it checks its image's identity, then re-opens the verified file allowing only renaming and deletion (never writing). Uninstall moves the running copy under a unique name into `%ProgramData%\SentinelAI-Setup` and schedules only that unique path for deletion at restart, so no pending deletion can ever hit a reused path and the product folders go at once. New installed copies are written completely under a temporary name before replacing the old one.
- **Known limitation, pre-existing:** the worker passes the one-use token to the pilot installer as a PowerShell parameter, as the full Setup does since TASK-024. If an organization enables PowerShell module logging for all modules by policy, the token can appear in the PowerShell Operational event log; it is consumed by the enrollment seconds later, or stops working when its code expires, is revoked or the install fails. Not changed in MVP-2.
- **Known limitation, pre-existing:** the full installation's folders use the pilot's `Container` kind with an entry for the installing administrator, so maintenance and uninstall of the central installation must be run by that administrator account. Not changed in MVP-2. Resolved by the 2026-10-26 administrators-only central installation entry below.
- **Quiet mode only for Agent Setup.** The full Setup keeps its interactive administrator creation and maintenance; its Apps entry opens that flow.

Only the earlier installing account itself could have put such an entry on the shared data root, and it could already change everything the migration then accepts.

## 2026-10-26 — MVP-5 removal of leftovers (owner decision)

- **Scope (owner decision).** The pilot ships one central Setup and one Agent Setup, so the browser dashboard, the manual pilot installation and the separate Agent and Desktop packages are removed. Every `.gitkeep` stays.
- **Core serves no browser application.** Without static files every path outside the API answers `404` on both listeners, which also removes the dashboard's CSP surface and the Node.js toolchain from the build.
- **One package layout.** The package script builds only the self-contained directories Setup installs, and the bundle carries only `PilotInstaller.psm1` and `CoreServiceInstaller.psm1`, the modules Setup loads. Setup's payload check names `bundle/installer/PilotInstaller.psm1` instead of the removed manual entry script.
- **CI fixtures, not a customer path.** The console Core launcher and the Core service management script drive the Windows Core service and Desktop UI acceptance over the same modules Setup uses, so they move to `tests/core-service/` rather than being deleted; that coverage stays. The verifier integration test is removed with the verifier.

## 2026-10-26 — MVP-6 detection on every Windows (owner decision)

- **Security log access (owner decision: access plus audit policy).** The narrowest option documented since TASK-027: the Agent service gets an unrestricted service SID and only that SID gets a read-only (0x1) entry on the Security channel. Event Log Readers was rejected because it grants every channel; LocalService because it grants every LocalService process; a new service account because it orphans the DPAPI-protected enrollment.
- **Audit policy.** Only success auditing of Other Object Access Events is turned on (4698); logon auditing is on by default and 1102 is always written. The subcategory is addressed by GUID through `AuditQuerySystemPolicy`/`AuditSetSystemPolicy`, never by localized `auditpol` names or output. The found setting is recorded in an administrators-only registry value, not in the Agent's LocalService-writable data directory, so another LocalService process cannot change what uninstall restores.
- **Restoration.** Uninstall restores only what Setup changed: the entry for the Agent's own SID and, if success auditing was off before, the success flag. An administrator's later change to failure auditing is kept. Revoke runs before the service is deleted, so a failed uninstall is retried whole. Domain Group Policy can override both settings; documented, not fought.
- **Language independence.** SCM's 7045/7040 texts are recognized through services.exe's own strings (its string table, read from each installed language's `services.exe.mui` by locale name, without depending on .NET culture data) rather than a translation table, so new languages need no code change. A text that maps to two values is dropped rather than guessed; English stays as the fallback, and numeric start types still map.


## 2026-10-27 — MVP-7 part 1: Agents update from Core (owner decisions)

- **Who installs (owner decision: "Zadanie SYSTEM + podpis").** The Agent runs as LocalService and cannot write code, so it only downloads; a SYSTEM scheduled task that Agent Setup registers runs the installed Updater, which trusts nothing the Agent wrote. Rejected: a SYSTEM-side downloader (a second network client and credential running as SYSTEM) and giving LocalService write access to its own code (a compromised Agent could persist).
- **What Core offers.** The signed Agent package of the same release travels inside Core's code (`Core\agent-update`), so it is replaced and rolled back atomically with the deployment and needs no separate store, upload route or database migration. Core does not verify it again: Core cannot authorize installation; every Agent computer verifies with its own pinned key and policy.
- **Trust on the Agent computer.** The Updater reads only Agent Setup's protected receipt and pinned key, refuses links in every path it reads, authenticates the manifest under that exact policy (key ID, `development` environment, channel, `sentinelai-agent-win-x64`, newer version) and installs from a private verified copy. It checks that the service is this installation's LocalService Agent before touching it, gives replaced code Agent Setup's exact access rules before starting it, and never writes into or deletes from the LocalService-writable data directory. The receipt version is rewritten in place so the file keeps its protected access rules.
- **Broken releases.** A rolled-back manifest's hash and count are kept in Agent Setup's protected data; after three rollbacks that release is not tried again, so a broken release cannot stop the Agent every hour while a one-off failure (for example a file still in use) is retried. The next release is installed normally.
- **Uninstall race.** Uninstall holds the task (disabled; a running update gets two minutes to finish or roll back, then is stopped) before removing the service, deletes it after, and enables it again if the service cannot be removed, so nothing is deleted while an unproven service remains.
- **Accepted limits.** The Updater and the installed Agent Setup copy on Agent computers are not updated (they keep working at their version); the central computer's own Agent is updated only by Setup's Upgrade with the whole deployment. The central update from the owner's server is part 2.

## 2026-10-27 — MVP-7 part 2: optional central update from the owner's server

- **Owner decisions.** The server address is built in at build time (`-UpdateServerUrl`); checking is off by default, so the pilot makes no internet connection; once an administrator turns checking on in Desktop, night-time installation is on by default; with it off, the administrator selects Install now.
- **What runs the upgrade.** The downloaded artifact is the signed full Setup (`sentinelai-setup-win-x64`), run as `/upgrade /quiet`, not a separate code-replacement path: the upgrade keeps every check of the interactive Upgrade (ownership, pinned trust, whole-deployment transaction, rollback, receipts, firewall, Security log access, Windows Apps). The full Setup's only quiet mode is this upgrade; it changes nothing that is not an owned, healthy, older installation.
- **Trust boundary.** Core (a network-facing service account) only downloads into its own data directory, from exactly the configured server, without redirects. The SYSTEM task (and Install now, elevated) treats the download as untrusted: it verifies the manifest with the key, environment and channel the full Setup pinned at installation and requires a newer version, copies the Setup into an Administrators/SYSTEM-only folder and checks the copy against the signed hash before running it. The attempt record lives there too (Core may only read it), so SYSTEM never writes into a folder Core can change.
- **Desktop at night.** Setup refuses to upgrade beside a running Desktop, and Desktop can run permanently in the notification area. The nightly task therefore closes this installation's Desktop (it holds no state of its own; the services keep monitoring) instead of postponing forever. Install now closes Desktop itself.
- **No waiting, at most three tries.** The Updater that verifies the download is part of the deployment the upgrade replaces, so it starts the verified Setup and exits. A release is started at most three times by the nightly task, so a broken release cannot restart the services every night; Install now always tries.
- **Download folder from Setup.** Core may create files but no folders in its data directory, so Setup provides `Core\central-update` (builds with a server only) with the data directory's rights: Core creates and changes its own files there and cannot remove the folder, create folders or change its permissions. A build without a server and uninstall (also when data is kept) remove it, so a later installation over retained data finds Core's data directory as before.
- **Start Menu account at night (owner decision of 2026-10-28).** Windows CI showed the nightly quiet upgrade, run as SYSTEM, refusing the installation (exit 13) because the shared Start Menu Programs folder lets the account that ran Setup write there, and the 2026-10-26 exception accepts only the account running Setup. The owner chose to remember that account: when an administrator installs, repairs or upgrades and that account itself has write access to the Programs folder, Setup records it in `%ProgramData%\SentinelAI-Setup\central-update\programs-writer.json` (Administrators and SYSTEM only); otherwise it removes the record. Only Setup running as SYSTEM accepts the recorded account, on that one folder, as a writer only, as the 2026-10-26 exception does for the account running Setup. An earlier installation without a record upgrades at night after its first repair or upgrade from the Setup window. A build without a server and uninstall remove the record.
- **Own task not reported.** Setup registers the nightly task before the Agent first starts and leaves an unchanged task alone. Restoring retained data recreates it while the Agent runs, which SA-EVT-PERSIST-003 reports once; the rule is not weakened with an exception for SentinelAI's own folder, because that folder would hide other tasks.

## 2026-10-31 — TASK-030: vulnerability and patch management (owner decisions)

- **Source and delivery (owner decision).** The owner builds a vulnerability feed from public NVD and CISA KEV data and signs it with the update key as artifact `sentinelai-vulnerability-feed`. Core downloads a newer one from the owner's update server while checking for updates is on (off by default), or an administrator imports the signed file in Desktop. Core never contacts NVD or CISA, so no evaluation needs the Internet.
- **Coverage (owner decision).** A curated list of common business programs plus Windows client releases (`tools/vulnerability-feed/products.json`). Server releases are not covered yet because the Agent reports their edition in the product name.
- **Trust.** Every Core build carries `update-trust.json` (development key ID, channel, public key), written at publish by `update-dev trust`. Core verifies the feed itself: signature and policy, artifact ID, exact size and SHA-256, the feed's own version equal to the manifest's, and newer than the feed in use (no rollback). It is stored in SQLite.
- **No claim without a reliable mapping.** The builder drops configurations that also need another vulnerable product, negated or nested conditions, other updates, editions or target platforms, and versions without bounds, and counts them in the feed. A platform condition holds when it names Windows, alone or among other platforms; a configuration limited to other platforms does not apply to Windows. The matcher claims a vulnerability only for one exact product match: display name, publisher and version form. Otherwise the program is ambiguous, unsupported-version or not covered, and that state is shown.
- **Alerts and Risk.** Fixed policy, no model: SA-VULN-001 critical (CISA KEV), SA-VULN-002 high (other, CVSS critical), SA-VULN-003 medium (other, CVSS high). Lower severities are listed but raise no alert. The rules are evaluated at telemetry ingest and scored as telemetry detections, so new data reaches alerts at each computer's next hourly report.
- **Freshness.** Version, build time, age (stale after 14 days), sources and retrieval times are shown in Settings and with every device assessment. No patch is executed.
