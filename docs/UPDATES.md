# Signed updates and setup lifecycle

The public-only verification library, local verification/staging client, development-only signing tool and transactional installation API support explicit signed code replacement and rollback. TASK-025 integrates that same foundation into `SentinelAI-Setup.exe` for whole-deployment upgrade, repair and recovery. Downloading releases, scheduling updates and unattended application updates remain unimplemented.

## Manifest and explicit trust

An update is a bounded UTF-8 JSON envelope with exactly `format`, `keyId`, `manifest` and `signature`. The format is `sentinelai-update-v1`. The nested manifest contains exactly:

- `version`: canonical numeric `major.minor.patch`, each component 0–65535;
- `artifactId`: the expected artifact identifier;
- `artifactUrl`: an HTTPS URL without credentials, query or fragment;
- `sha256`: 64 lowercase hexadecimal characters for the complete ZIP bytes;
- `sizeBytes`: the exact compressed byte count, greater than zero and at most 512 MiB;
- `channel`: `stable`, `pilot` or `beta`;
- `environment`: `development` or `production`.

The client pins the expected environment, channel, artifact identifier, installed version and named public SPKI P-256 trust anchors. Pilot and Beta are explicit opt-in channels; neither is accepted under Stable policy. Development manifests are rejected under Production policy even if their public key is accidentally supplied there. Keys are provisioned locally, not downloaded from the manifest. Update keys are separate from licensing keys and Agent credentials.

ECDSA P-256/SHA-256 signs the canonical JSON containing the format, key ID and all manifest fields. The signature is a fixed 64-byte IEEE P1363 value encoded as canonical unpadded base64url. There is no algorithm negotiation. Missing/duplicate/unknown fields, malformed types, oversized documents, invalid signatures and policy mismatches fail closed. The maximum manifest size is 8 KiB. Ordinary upgrade candidates must be strictly newer than the configured installed version; an authenticated installed receipt also prevents applying a stale candidate when the caller's version floor is outdated. Explicit repair accepts only the authoritative installed version. Restoration of an empty owned code directory accepts an equal or newer version against the retained floor; it does not create a downgrade exception.

Public verification code contains no private-key importer or signer. Production private keys and production signing stay outside this repository and the client. The separate development tool generates disposable development keys outside the checkout, uses only `dev-` key IDs and always signs `environment: development`; it has no production mode. Unix private key files are owner-only; Windows key directories require account-restricted ACLs. Private PEM files are also ignored by Git as a secondary guard.

## Local development workflow

From a Windows PowerShell terminal at the repository root, use a separate directory under local application data. The example uses version `1.1.0` over an explicitly known installed `1.0.0`; choose the actual versions for your installation.

```powershell
$updateWork = Join-Path $env:LOCALAPPDATA 'SentinelAI\UpdateDevelopment'
New-Item -ItemType Directory -Force -Path $updateWork | Out-Null
dotnet run --project tools/update-dev -- keygen --directory "$updateWork\keys" --key-id dev-local

dotnet publish agent/SentinelAI.Agent.csproj -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true -p:DebugType=none -p:DebugSymbols=false -p:Version=1.1.0 -p:AssemblyVersion=1.1.0.0 -o "$updateWork\agent-code"
Compress-Archive -LiteralPath "$updateWork\agent-code\SentinelAI.Agent.exe" -DestinationPath "$updateWork\agent-1.1.0.zip"

dotnet run --project tools/update-dev -- sign --private-key "$updateWork\keys\dev-local.private.pem" --key-id dev-local --package "$updateWork\agent-1.1.0.zip" --version 1.1.0 --artifact-id sentinelai-agent-win-x64 --artifact-url https://updates.example.invalid/agent-1.1.0.zip --channel pilot --output "$updateWork\agent-1.1.0.manifest.json"

dotnet run --project updater -- verify --manifest "$updateWork\agent-1.1.0.manifest.json" --package "$updateWork\agent-1.1.0.zip" --public-key "$updateWork\keys\dev-local.public.pem" --key-id dev-local --environment development --channel pilot --artifact-id sentinelai-agent-win-x64 --installed-version 1.0.0
```

The example artifact URL is metadata; these commands make no network request. Generate each key pair once; existing keys/manifests/packages are not overwritten. The signing tool does not infer the executable's version, so publish the artifact with the same explicit version that is signed. Legacy installations need an operator-supplied current version floor. The existing Agent's assembly version includes a fourth component; the update policy uses its first three numeric components.

The client `stage` command accepts the same flags as `verify` plus `--output ABSOLUTE_NEW_FILE`. Choose an output directory controlled by the operator, with account-restricted ACLs on Windows. Both commands verify the signature and stream the exact package into a new private copy while checking its signed hash and size. Verification deletes its temporary copy; staging retains the verified ZIP. These commands do not extract code, stop a service or install anything. A staged ZIP is not an authorization bypass: installation verifies it again under the current policy.

TASK-015 adds `prepare`, with the same flags plus `--output ABSOLUTE_NEW_DIRECTORY`, for fresh pilot installation. It uses the authenticated private copy and the existing bounded ZIP extractor, accepts only the expected Core/Agent executable layout and rejects known persistent state and installed-receipt aliases. The parent must already be operator-controlled; existing destinations and links are refused. It leaves only the prepared code tree and performs no service operation or health assertion. Preparation of a local package takes seconds, and on a slow disk at most a minute or two, so `prepare` stops after 5 minutes: it removes its partial output and private copy, writes one fixed line to standard error and exits with code 2. The pilot installer and Setup run it as a child process that they kill after 330 seconds. Either case fails the installation step closed with its existing fixed message (Setup reports the failed step); no service or installed code has changed, and a retry prepares into a new directory. [Setup](SETUP.md) provisions Windows ACLs and uses this command before installation. Its installer modules and verifier must themselves come from a trusted source; a manifest-provided/publicly delivered key is not automatic trust.

## Installation and rollback API

`TransactionalUpdater.InstallAsync` takes the raw signed manifest, local ZIP path, explicit verification policy, existing absolute code-only installation directory, and an `IServiceUpdateLifecycle` adapter. `RepairAsync` uses the same transaction for authenticated equal-version code repair. `RestoreAsync` requires an empty owned code directory and retains the version floor while restoring equal/newer code. These are library APIs, not unattended CLI installation commands.

Supported artifacts are `sentinelai-agent-win-x64` / `SentinelAI.Agent.exe`, `sentinelai-core-win-x64` / `SentinelAI.Core.exe`, and `sentinelai-deployment-win-x64`. The whole-deployment layout contains exactly the Core, Agent, Desktop and Updater code trees plus authenticated `deployment-version.json`; its version must match the signed manifest. There is no default adapter that assumes a service is healthy. The host must implement stopping, starting and checking the actual updated service, honor cancellation and bound service-control operations. Setup supplies the real Windows ownership/service adapter for its supported default installation.

Persistent Core/Agent data and operator secrets/configuration must remain outside the installation code directory. Keep the service account stable so Windows DPAPI enrollment state remains usable. Setup keeps these under protected ProgramData, separate from replaceable `%ProgramFiles%\SentinelAI`; console development's LocalApplicationData state also remains separate from code. Existing code/state is not migrated by the updater.

Before stopping the service, the installer authenticates the manifest, verifies a private immutable package copy and validates/extracts the archive into a private sibling directory. Component ZIP limits are 1,024 entries and 512 MiB expanded bytes; the bounded whole-deployment layout allows 4,096 entries and 1 GiB expanded bytes, while signed compressed packages remain at most 512 MiB; only the full Setup executable offered by an update server (`sentinelai-setup-win-x64`, MVP-7) may be up to 1 GiB, because it carries the Setup host's runtime beside its payload. Traversal, absolute paths, Windows ADS/device aliases, invalid filenames, duplicate/colliding paths, links/reparse points and missing expected executables are rejected. Known persistent SentinelAI state files are rejected in both the existing code tree and the package. Packages cannot supply an installed receipt. Repair can restore missing executable/marker files without accepting persistent state into code. Update directories and their parent must be controlled by the updater/service operator; Unix installation parents writable by group/other accounts are rejected, and Windows requires operator-provisioned restricted ACLs. The mechanism is not protection against a privileged local owner replacing storage.

An exclusive installation lock and durable journal coordinate the transaction. The old code is moved to a backup; staged code replaces it at the same installation path. Only successful service start and health verification commit the signed receipt/version. For upgrade/repair of an installed deployment, installation/start/health failure or cancellation restores the previous directory, restarts the previous service and verifies its health using an independent bounded recovery token. Retained restoration instead starts from an empty owned code directory; it has no previous running code to restart.

If rollback itself fails, the result is `RollbackFailed`, and backup/work files plus the journal remain for retry; success is never reported. `RecoverAsync` authenticates pending journal metadata and restores incomplete transactions, including interruption between renames and journal writes. A committed healthy transaction can finish cleanup without undoing its successful update. The journal has fixed, derived sibling paths rather than caller-supplied destinations. Files and journal records are flushed before proceeding; this is process-interruption recovery, not a claim of filesystem durability through every power-loss/storage failure.

## Setup integration

Setup detects the protected owned default deployment, compares canonical versions and rechecks ownership under an exclusive operation lock. Maintenance pins the installed public key, key ID, channel/environment and protected version receipts; the candidate Setup key cannot become replacement authority. A whole-deployment transaction replaces Core, Agent, Desktop and Updater together, preserving Core SQLite, administrator/installation/endpoint identity, enrollment, Agent DPAPI state, configuration and licensing data. It does not initialize an administrator again, re-enroll Agent or migrate state.

Close Desktop before maintenance. Equal-version Setup offers repair, newer Setup offers upgrade, and older Setup offers only uninstall. Owned data retained after uninstall can restore authenticated code/services at the retained or a newer version. Interrupted transactions require the native **Recover installation** action before another operation. Uninstall removes owned services/code/shortcut and retains data by default; clearing that option requires the exact **DELETE** confirmation. See the [Setup guide](SETUP.md#repair-upgrade-and-uninstall) for the operator workflow.

## Automatic Agent updates from Core (MVP-7)

Agents installed by Agent Setup update themselves from the central computer; nothing is downloaded from the internet and Core makes no outbound connection.

- **Offer.** The full Setup's Core code carries the release's signed Agent package (`Core\agent-update\agent.zip` and `agent.manifest.json`, added by `scripts/publish-pilot-windows.ps1`), so upgrading the central installation offers its Agent version to every Agent. Core serves the two files only to enrolled Agents: `GET /api/agent/update/manifest` and `GET /api/agent/update/package` require the Agent credential, answer `no-store`, only over HTTPS or loopback, at most 10 requests per minute per address, and 404 without a package. On the local-network listener they are the only `GET` routes. `SentinelAI:AgentUpdate:Directory` (absolute) overrides the folder for development.
- **Download.** One minute after linking to Core and then hourly (15 minutes after a failed check), the Agent compares the offered version with its own. It streams a newer Agent package into `<Agent data>\update` and keeps it only if size and SHA-256 match the manifest, writing the manifest last. A package that is not newer is removed, which also clears it after an update. The Agent does not decide trust and cannot install: LocalService has no write access to code.
- **Installation.** Agent Setup registers the task `\SentinelAI\SentinelAI Agent Update`: SYSTEM, hourly with up to 10 minutes' random delay and 5 minutes after startup, missed runs caught up, never two at once, at most one hour per run. It runs `SentinelAI.Updater.exe apply-agent-update`, which:
  1. requires SYSTEM or an administrator and refuses unless the `SentinelAIAgent` service runs this installation's Agent and configuration as LocalService;
  2. reads Agent Setup's protected receipt (exact fields, `development` environment) and pinned public key, and finishes or undoes an interrupted transaction;
  3. treats the staged files as untrusted: links and reparse points are refused; the manifest must verify with the pinned key ID, environment and channel, name `sentinelai-agent-win-x64` and be newer than the installed version; the package is copied privately and checked against the signed hash;
  4. replaces `%ProgramFiles%\SentinelAI Agent\Agent` through the transactional updater, gives the new code Agent Setup's access rules, starts the service and requires it to keep running for 15 seconds, otherwise restores the previous Agent. A release that was rolled back three times is not tried again (its manifest hash and count are kept in Agent Setup's protected data), so a broken release cannot restart the Agent every hour while a one-off failure is retried; the next release is installed normally;
  5. on success writes the new version into the receipt, in place so it keeps its access rules, and into the Windows Apps entry.

  It never writes into or deletes from the Agent's data directory. Exit codes: 0 no update or installed, 3 rejected (the Agent was not stopped), 4 rolled back, or a release given up after three rollbacks, 5 rollback failed (recovery is retried at the next run), 1 any other failure.
- **Uninstall** holds the task first (no new run; a running one gets two minutes before it is stopped), removes the service and then deletes the task; if the service cannot be removed, the task is enabled again.
- **Not updated automatically:** the central computer's own Agent (Setup's **Upgrade** replaces it with the whole deployment), the Updater and the installed Agent Setup copy on Agent computers (they keep working at their installed version), and Agents installed without Agent Setup.

## Optional central update from the provider's server (MVP-7 part 2)

Owner decisions of 2026-10-27: the server address is built in at build time; checking is off by default, so a pilot installation makes no internet connection; once an administrator turns checking on, night-time installation is on by default, and with it off the administrator selects **Install now**.

- **Server, built in.** `scripts/publish-pilot-release-windows.ps1 -UpdateServerUrl https://…` (and `publish-setup-windows.ps1`) writes `update-server.json` (URL and channel) into Core's code and signs the full Setup with the update key as artifact `sentinelai-setup-win-x64` in `SentinelAI-Setup.manifest.json`. Upload that manifest to `<URL>/SentinelAI-Setup.manifest.json` and the Setup to `<URL>/<version>/SentinelAI-Setup.exe`; nothing else is requested. The URL is a lowercase `https://` address without credentials, query, fragment or trailing slash. A build without it has no update settings and no nightly task.
- **Checking (off by default).** Desktop → Settings → Updates. While off, Core makes no connection for updates and keeps no download. While on, Core requests the manifest two minutes after start, every six hours (an hour after a failed check) and on **Check now**; it never follows redirects and accepts only this channel's development-environment Setup manifest whose artifact URL is exactly `<URL>/<version>/SentinelAI-Setup.exe`. A newer Setup is streamed into `%ProgramData%\SentinelAI\Core\central-update` (a folder Setup provides, because Core may create files but no folders in its data directory) and kept only with the manifest's exact size and SHA-256; the manifest is written last. Core does not decide trust. Routes: `GET /api/admin/updates`, `POST /api/admin/updates/settings` with `checkEnabled` and `autoInstall` (404 without a server), and `POST /api/admin/updates/check` (409 without a server or while off).
- **Night-time installation.** A build with a server gets the task `\SentinelAI\SentinelAI Update`: SYSTEM, daily at a random time between 02:00 and 04:00, a missed night is not caught up. Setup registers it before the Agent first starts and leaves an unchanged task alone. It runs `SentinelAI.Updater.exe apply-central-update`, which acts only while Core's `auto-install` marker shows that automatic installation is on, and:
  1. requires SYSTEM or an administrator, and reads the full Setup's protected receipt (development key ID, environment, channel), its pinned public key and Core's installed version;
  2. treats the download as untrusted: links are refused, the manifest must verify with that key and policy, name `sentinelai-setup-win-x64` and be newer than the installed version;
  3. copies the Setup into a new folder under `%ProgramData%\SentinelAI-Setup\central-update` (Administrators and SYSTEM only) and checks the copy against the signed hash;
  4. records the attempt in `state.json` there, which only Core's service account may also read, closes this installation's Desktop (it keeps no state; the services keep monitoring) and starts the copy with `/upgrade /quiet` without waiting, because the upgrade replaces the Updater too;
  5. tries one release at most three times; a later release starts counting again.

  The Setup then performs exactly the interactive **Upgrade**: the same ownership checks, pinned trust, whole-deployment transaction and rollback. Exit codes of the scheduled run: 0 started or nothing to do, 3 rejected, 4 given up after three attempts.
- **Install now.** Desktop runs `apply-central-update --now` elevated (Windows asks for administrator approval). It verifies the download the same way, opens the Setup window with **Upgrade** selected and Desktop closes. Exit codes: 0 started, 6 nothing newer is downloaded, 3 rejected.
- **`SentinelAI-Setup.exe /upgrade /quiet`** exit codes: 0 upgraded; 1 failed; 2 invalid command line; 13 nothing to upgrade (no owned healthy installation older than this Setup); 14 Desktop is running; 15 the upgrade failed and the previous version was restored; 16 recovery is needed (run Setup interactively); 1603 and 1460 as for the native wrapper.
- **Vulnerability data (TASK-030).** The same checking switch also fetches newer signed vulnerability data from the same server: `<URL>/vulnerability-feed.manifest.json` and `<URL>/vulnerability-feed/<version>/vulnerability-feed.json`, signed as artifact `sentinelai-vulnerability-feed`. Core verifies it itself with the update trust built into every Core (`update-trust.json`); see [vulnerabilities](VULNERABILITIES.md).
- **Limits.** The previous run's copy is removed by the next run. Uninstall holds the task, then removes it. Restoring retained data creates the task while the Agent runs, so SA-EVT-PERSIST-003 reports that one task once. Agents on the other computers then update from Core (part 1).

## Verification

`./scripts/build.sh` builds the library and tools; `./scripts/test.sh` runs `SentinelAI.Updates.Tests` and portable Setup tests. Tests use generated temporary development keys and synthetic packages, never production credentials. They cover signature/metadata/hash tampering, strict format/trust/channel/version checks, private staging, malformed archives, whole-deployment replacement, equal-version damaged-code repair, retained restoration, health/cancellation rollback and interruption recovery with scripted service lifecycles. Portable Setup tests cover state/version/action restrictions and explicit data-removal/cancellation guards.

`SentinelAI.Core.Tests`, `SentinelAI.Agent.Tests` and `SentinelAI.Updates.Tests` cover the MVP-7 routes (credential, rate limit, bounds), the Agent's staging (tampered, short, long, foreign, older and malformed offers) and the SYSTEM side (pinned key, channel, artifact, linked staging, strict receipt, a rolled-back release given up after three attempts). The native Agent Setup acceptance installs an older Agent Setup beside a newer central installation and checks that the SYSTEM task updates the same enrolled endpoint. For part 2, Core tests cover the server file, settings, exact downloads and refusals (channel, artifact, address, redirect, size, damaged copy); Updates tests the central installer (night-time switch, three attempts, tampered, foreign, other channel or artifact, linked folder, strict receipt); Setup tests the quiet upgrade outcomes; Desktop tests the Updates client, view model and view. The native fresh-install acceptance checks the nightly task and that checking is off; the lifecycle acceptance has the nightly task upgrade 1.1.0 to a signed 1.3.0 Setup staged as Core stores it, closing Desktop and keeping data and identity.

TASK-025's actual Windows lifecycle acceptance passed in both push and PR CI. The [native Setup fixture](SETUP.md#validation) executes published installers, real services and native controls for upgrade, health-failed rollback, damaged-file repair, retained-data uninstall/restoration and explicit confirmed removal. It verifies protected state, identity, enrollment, DPAPI, licensing and history preservation alongside actual service/ACL behavior. Exact results and commits are recorded in [STATUS](../.agent/STATUS.md).
